# Specification-Driven Development

Этот каталог — **источник истины для поведения**. Значимое изменение начинается со
**спецификации**, а не с кода: дизайн обсуждается в тексте (дешевле менять решение), человек
и ассистент работают от одного документа, объём защищён от расползания.

## Когда спека обязательна

- Новая фича или изменение видимого поведения редактора.
- Изменение **публичного контракта**: экспортные функции моста (`window`/`defaultView` — `init`,
  `setText`, `getText`, `updateMetadata`, `compare`, …), набор событий (`EVENT_*`), формат
  доставки бандла (сборка, single-file), поддерживаемые платформы/движки.
- Изменение затрагивает несколько модулей/слоёв сборки.

## Когда спека НЕ нужна

Опечатка, локальный багфикс без изменения контракта, рефактор без изменения поведения, бамп
зависимостей, правка комментариев/доков.

## Структура спеки

Активная спека — **папка** `specs/<id>/` с двумя файлами:

- [`spec.md`](_template/spec.md) — **стабильный контракт**: контекст, поведение, публичные контракты,
  критерии приёмки. Переживает merge, уезжает в `specs/done/<id>/spec.md`.
- [`plan.md`](_template/plan.md) — **транзиентный** план + открытые вопросы + журнал решений. Живёт
  до закрытия задачи; после merge либо удаляется, либо уезжает в `specs/done/<id>/` как архив развития.

Разделение снимает две проблемы: в ревью/контексте не мешают пройденные этапы и журнал решений, а
после merge не надо перечитывать сотни строк заметок, чтобы вспомнить, что гарантирует фича.

**Порог `decisions.md`:** при ~15+ записях в разделе «Решения» — вынести их в соседний `decisions.md`.
Для типовой задачи (3–7 решений) — держать в хвосте `plan.md`.

## Идентификатор `<id>`

- Есть issue → `specs/<N>/` (напр. `specs/18/` для issue #18).
- Работа без issue (спайк/подготовка) → короткий kebab-slug (`specs/single-file-build/`,
  `specs/monaco-0.55/`). Заведётся issue — можно связать через поле `issue` во фронтматтере.

Описательное название живёт в поле `title` фронтматтера, а не в имени папки.

## Процесс

1. Перед кодом — папка `specs/<id>/`, копируются оба файла из `specs/_template/`. Статус `draft`.
2. Спека согласуется (по вопросам публичного контракта/обвязки — с мейнтейнером). Статус → `approved`.
3. Только после `approved` — рабочая ветка от нужной базы, код. Статус → `in-progress`.
4. Коммиты ссылаются на issue (если есть) и на спеку.
5. Расхождение кода и `spec.md` — обновляется **спека тем же PR**, не задним числом. Транзиентное
   (этапы, решения) — в `plan.md`.
6. После merge и закрытия задачи — статус → `done`, папка переносится в `specs/done/<id>/`.
   `superseded` и ретро-спеки не переносятся.

## Ретроактивное покрытие

Чтобы задокументировать существующее поведение (обвязка редактора, контракт моста, грамматика BSL),
пишется спека без issue (`issue: retro`), описывающая **текущее** поведение как контракт. Обнаруженные
несоответствия/долги — отдельными issue и спеками. Ретро-спеки — одиночным файлом `specs/retro/<тема>.md`
(без папочной структуры spec/plan), в `done/` не переносятся.

## Статусы

| Статус | Значение |
| --- | --- |
| `draft` | Черновик, обсуждается |
| `approved` | Согласована, можно кодить |
| `in-progress` | Код в работе |
| `done` | Смержено, задача закрыта; папка в `specs/done/<id>/` |
| `superseded` | Заменена другой спекой (указать какой); остаётся рядом с заменяющей |

## Именование файлов

- `specs/<id>/spec.md` + `specs/<id>/plan.md` — активная спека.
- `specs/<id>/decisions.md` — опционально, при 15+ решениях.
- `specs/done/<id>/…` — завершённая спека.
- `specs/retro/<тема>.md` — ретро-спека одиночным файлом.
- `specs/_template/…` — шаблоны (не править, копировать).
